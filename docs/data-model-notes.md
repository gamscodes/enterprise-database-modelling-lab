# Data Model Notes

> **Portfolio Project:** Enterprise Citizen Licensing & Permit Management Platform  
> **Database:** PostgreSQL  
> **Document Purpose:** Explain the logical data model, entity relationships, design decisions, and data integrity approach.

## 1. Entity Identification

The entities in this model were identified by analyzing the business requirements and business rules for the simulated Citizen Licensing & Permit Management Platform.

The model contains 14 entities grouped into seven functional areas.

### 1.1 Citizen Management
- `citizens`
- `citizen_profiles`

### 1.2 Application Management
- `application_types`
- `applications`
- `application_status_history`

### 1.3 Document Management
- `documents`
- `application_documents`

### 1.4 Review and Approval
- `application_reviews`
- `application_approvals`

### 1.5 Financial Management
- `payments`

### 1.6 Security and Access Management
- `users`
- `roles`
- `user_roles`

### 1.7 Audit
- `audit_logs`

These entities represent the major business objects and activities required by the simulated platform.

## 2. Entity Count and Scope

The logical data model contains **14 entities**, implemented as relational tables in PostgreSQL.

The design was reviewed for:

- Business relevance and requirement coverage
- Entity relationships and cardinality
- Normalization and duplication
- Primary and foreign key design
- Referential integrity and data quality
- Security, traceability, and auditability
- Maintainability and future extensibility

The model focuses on structured relational data. Actual document files, application user interfaces, authentication services, and external payment processing are outside the scope of this database portfolio implementation.

## 3. Entity Definitions

### 3.1 `citizens`

**Purpose:** Stores the core identity information for each citizen using the simulated platform.

**Design rationale:** A citizen may submit multiple applications. Separating citizen information from application transactions reduces repeated identity data.

**Key attributes:**
- `citizen_id` - Primary key generated by PostgreSQL.
- `first_name` and `last_name` - Required identity fields.
- `date_of_birth` - Date of birth, subject to a database validation rule.
- `created_at` - Record creation timestamp.
- `updated_at` - Timestamp initialized when the record is inserted.

**Design decisions:**
- Required identity fields are protected by `NOT NULL` and data-quality constraints.
- Applications reference citizens through a foreign key.
- The `updated_at` default does not automatically change when a record is updated. Automatic maintenance would require an additional mechanism, such as a trigger or application logic.

**Relationships:**
- One citizen may have multiple applications.
- One citizen may have one associated profile.

### 3.2 `citizen_profiles`

**Purpose:** Stores additional contact and address information associated with a citizen.

**Design rationale:** Separating profile information from core identity information provides a clear structure for maintaining contact and address attributes.

**Key attributes:**
- `citizen_id` - Both the primary key and a foreign key to `citizens`.
- `email_address` and `phone_number` - Contact information.
- `address_line_1`, `address_line_2`, `city`, `province_code`, and `postal_code` - Address information.
- `created_at` and `updated_at` - Profile timestamps.

**Design decisions:**
- Using `citizen_id` as both primary and foreign key enforces a maximum of one profile record per citizen.
- The foreign key prevents a profile from referencing a nonexistent citizen.
- The `updated_at` default initializes the timestamp at insertion; it does not automatically track subsequent updates.

**Relationship:** One citizen can have zero or one profile, and each profile belongs to exactly one citizen.

### 3.3 `application_types`

**Purpose:** Maintains the controlled list of licence and permit types available through the platform.

**Design rationale:** A reference table avoids repeatedly storing application-type descriptions and provides consistent values for application records.

**Key attributes:**
- `application_type_id` - Primary key.
- `type_code` - Unique business code.
- `type_name` - Required application-type name.
- `description` - Description of the type.
- `application_fee` - Fee stored using an exact numeric data type.
- `is_active` - Indicates whether the type is available for use.
- `created_at` and `updated_at` - Record timestamps.

**Design decisions:**
- `type_code` is unique.
- The database prevents negative application fees.
- Inactive types can be retained for historical reference and reporting.

**Relationship:** One application type may be associated with multiple applications.

### 3.4 `applications`

**Purpose:** Stores licence and permit applications submitted by citizens.

**Design rationale:** Applications are the central transactional entity in the model and connect citizen records, application types, reviews, decisions, documents, status history, and payments.

**Key attributes:**
- `application_id` - Primary key.
- `citizen_id` - Foreign key to `citizens`.
- `application_type_id` - Foreign key to `application_types`.
- `application_number` - Unique business identifier.
- `current_status` - Current application status.
- `submitted_at` - Submission timestamp, which may be `NULL` before submission.
- `created_at` and `updated_at` - Record timestamps.

**Design decisions:**
- `application_number` is unique.
- Foreign keys enforce valid citizen and application-type references.
- `current_status` supports operational queries without requiring the full history to be retrieved.
- Status changes are also represented in `application_status_history`.
- Application workflow rules that require coordination between multiple records may need application-level validation.

# 3. Entity Definitions

## 3.1 `citizens`

### Purpose

Stores the core identity information for each citizen using the simulated platform.

### Why it is needed

A citizen may submit multiple applications. Storing citizens as a separate entity prevents citizen information from being repeatedly stored within application records.

### Business Requirements Supported

* FR-01 — Citizen Management
* FR-04 — Application Submission
* FR-14 — Application Search and Filtering

### Business Rules Supported

* BR-01 — Unique Citizen
* BR-02 — Required Citizen Information
* BR-03 — Citizen Applications

### Initial Attributes

| Attribute       | Purpose                           |
| --------------- | --------------------------------- |
| `citizen_id`    | Unique identifier for the citizen |
| `first_name`    | Citizen's first name              |
| `last_name`     | Citizen's last name               |
| `date_of_birth` | Citizen's date of birth           |
| `created_at`    | Record creation timestamp         |
| `updated_at`    | Record modification timestamp     |

### Key Design Decisions

* `citizen_id` is the primary key.
* The identifier is generated by PostgreSQL.
* Required identity fields are defined as `NOT NULL`.
* Basic data-quality rules are enforced using `CHECK` constraints.

### Relationship

One citizen may submit many applications.

```text
citizens 1 → many applications
```

## 3.2 `citizen_profiles`

### Purpose

Stores additional contact and address information associated with a citizen.

### Why it is needed

Core identity information is separated from profile information to maintain a clear logical structure and allow the profile to expand independently.

### Business Requirements Supported

* FR-01 — Citizen Management
* FR-02 — Citizen Profile Management

### Initial Attributes

| Attribute        | Purpose                        |
| ---------------- | ------------------------------ |
| `citizen_id`     | Associated citizen             |
| `email_address`  | Email address                  |
| `phone_number`   | Primary phone number           |
| `address_line_1` | Primary address                |
| `address_line_2` | Additional address information |
| `city`           | City                           |
| `province_code`  | Province or territory code     |
| `postal_code`    | Postal code                    |
| `created_at`     | Profile creation timestamp     |
| `updated_at`     | Profile modification timestamp |

### Key Design Decisions

`citizen_id` is both:

* The primary key of `citizen_profiles`
* A foreign key to `citizens`

This creates a one-to-one relationship.

### Relationship

```text
citizens 1 → 1 citizen_profiles
```

## 3.3 `application_types`

### Purpose

Stores the controlled list of licence and permit types available through the platform.

### Why it is needed

Application types should not be stored as unrestricted descriptive text inside the `applications` table.

A reference entity provides:

* Consistent values
* Centralized maintenance
* Reusable application type definitions
* Reduced duplication

### Business Requirements Supported

* FR-03 — Licence and Permit Types
* FR-04 — Application Submission

### Initial Attributes

| Attribute             | Purpose                                           |
| --------------------- | ------------------------------------------------- |
| `application_type_id` | Unique application type identifier                |
| `type_code`           | Short business code                               |
| `type_name`           | Licence or permit name                            |
| `description`         | Description of the type                           |
| `application_fee`     | Applicable fee                                    |
| `is_active`           | Indicates whether the type is currently available |
| `created_at`          | Creation timestamp                                |
| `updated_at`          | Modification timestamp                            |

### Key Design Decisions

* `application_type_id` is the primary key.
* `type_code` must be unique.
* `application_fee` cannot be negative.
* Inactive application types can be retained for historical reporting.

### Relationship

One application type may be associated with many applications.

```text
application_types 1 → many applications
```

## 3.4 `applications`

### Purpose

Stores licence and permit applications submitted by citizens.

### Why it is needed

Applications are the primary transactional entity within the platform.

### Business Requirements Supported

* FR-04 — Application Submission
* FR-05 — Application Status Management
* FR-14 — Application Search and Filtering
* FR-15 — Operational Reporting

### Business Rules Supported

* BR-05 — Application Ownership
* BR-06 — Application Type
* BR-07 — Application Status
* BR-09 — Application History

### Initial Attributes

| Attribute             | Purpose                            |
| --------------------- | ---------------------------------- |
| `application_id`      | Unique application identifier      |
| `citizen_id`          | Citizen submitting the application |
| `application_type_id` | Licence or permit type             |
| `application_number`  | Human-readable business identifier |
| `current_status`      | Current application status         |
| `submitted_at`        | Application submission timestamp   |
| `created_at`          | Record creation timestamp          |
| `updated_at`          | Record modification timestamp      |

### Key Design Decisions

* `application_id` is the primary key.
* `application_number` is unique.
* `citizen_id` references `citizens`.
* `application_type_id` references `application_types`.

* Historical status changes are stored separately.

```text
citizens 1 → many applications

application_types 1 → many applications
```

## 3.5 `application_status_history`

### Purpose

Stores historical status changes for applications.

### Why it is needed

The current application status alone does not provide a complete history of the application's lifecycle.

A separate history entity preserves each status change as an individual record.

### Business Requirements Supported

* FR-05 — Application Status Management
* FR-06 — Application Status History
* FR-15 — Operational Reporting

### Business Rules Supported

* BR-09 — Application History
* BR-10 — Historical Status Preservation

### Initial Attributes

| Attribute            | Purpose                            |
| -------------------- | ---------------------------------- |
| `status_history_id`  | Unique history record              |
| `application_id`     | Associated application             |
| `status_code`        | Status assigned to the application |
| `changed_by_user_id` | User or process responsible        |
| `changed_at`         | Status change timestamp            |
| `reason`             | Optional reason                    |
| `comments`           | Optional comments                  |

### Key Design Decision

Each status change creates a new record instead of overwriting historical information.

This supports traceability and operational reporting.

### Relationship

```text
applications 1 → many application_status_history
```

## 3.6 `documents`

### Purpose

Stores metadata describing supporting documents submitted through the platform.

### Why it is needed

Document metadata is separated from application records to prevent document information from being duplicated.

### Business Requirements Supported

* FR-07 — Supporting Document Management

### Initial Attributes

| Attribute         | Purpose                      |
| ----------------- | ---------------------------- |
| `document_id`     | Unique document identifier   |
| `document_type`   | Type of document             |
| `file_name`       | Original file name           |
| `file_reference`  | Reference to stored document |
| `uploaded_at`     | Upload timestamp             |
| `document_status` | Current document status      |
| `created_at`      | Creation timestamp           |

### Key Design Decision

The relational database stores document metadata and a reference to the document location rather than the binary document content.

This keeps the relational model focused on structured metadata while allowing document storage to be handled by an appropriate storage service.

---

## 3.7 `application_documents`

### Purpose

Associates supporting documents with applications.

### Why it is needed

An application may contain multiple supporting documents. A separate association entity provides a normalized relationship between applications and documents.

### Business Requirements Supported

* FR-07 — Supporting Document Management

### Initial Attributes

| Attribute                 | Purpose                           |
| ------------------------- | --------------------------------- |
| `application_document_id` | Unique relationship identifier    |
| `application_id`          | Associated application            |
| `document_id`             | Associated document               |
| `document_purpose`        | Reason the document was submitted |
| `created_at`              | Association timestamp             |

### Key Design Decisions

* The table contains foreign keys to both `applications` and `documents`.
* The combination of `application_id` and `document_id` is unique.
* This prevents the same document from being linked to the same application more than once.

### Relationship

```text
applications many ↔ many documents
```

The many-to-many relationship is resolved through `application_documents`.

## 3.9 `application_approvals`

### Purpose

Stores formal approval, rejection, or return decisions for applications.

### Why it is needed

Approval decisions therefore require a separate entity.

### Business Requirements Supported

* FR-09 — Approval Decisions

### Business Rules Supported

* BR-15 — Approval Decision
* BR-16 — Decision Maker
* BR-17 — Decision Date
* BR-18 — Decision Integrity

### Initial Attributes

| Attribute          | Purpose                    |
| ------------------ | -------------------------- |
| `approval_id`      | Unique approval identifier |
| `application_id`   | Application being decided  |
| `approver_user_id` | User making the decision   |
| `decision`         | Approval decision          |
| `decision_at`      | Decision timestamp         |
| `comments`         | Decision comments          |

### Key Design Decisions

# 5. Normalization Approach

The model follows a normalized relational design.

Major business concepts are separated into independent entities rather than storing repeated information within a single large table.

Examples include:

* Citizen information is separated from applications.
* Application types are separated from application transactions.
* Status history is separated from the current application status.
* Documents are separated from applications.
* Reviews are separated from approval decisions.
* Payments are separated from applications.
* Users and roles are separated through a junction table.

This approach reduces:

* Data duplication
* Update anomalies
* Inconsistent values
* Repeating groups
* Maintenance complexity

Many-to-many relationships are resolved through association entities such as:

* `application_documents`
* `user_roles`

---

# 6. Primary Key Strategy

Each major entity has a dedicated primary key.

Primary key columns follow the naming convention:

```text
<table_name_singular>_id
```

Examples:

```text
citizen_id
application_id
document_id
payment_id
user_id
```

PostgreSQL identity columns are used where appropriate to automatically generate unique identifiers.

The `citizen_profiles` table uses `citizen_id` as its primary key because the profile represents a one-to-one extension of the citizen entity.

---

# 7. Foreign Key Strategy

Foreign keys enforce relationships between related entities.

Examples include:

```text
applications.citizen_id
        ↓
citizens.citizen_id
```

```text
applications.application_type_id
        ↓
application_types.application_type_id
```

```text
payments.application_id
        ↓
applications.application_id
```

```text
application_reviews.reviewer_user_id
        ↓
users.user_id
```

Foreign keys provide database-level referential integrity and prevent dependent records from referencing nonexistent parent records.

# 8. Data Integrity Strategy

The physical schema will enforce important business rules using database constraints.

### NOT NULL

Used where an attribute is required for a valid record.

Examples include:

* Application ownership
* Application type
* Application number
* Payment amount
* Approval decision
* Audit action

### UNIQUE

Used where duplicate values would create data integrity issues.

Examples include:

* `users.username`
* `users.email_address`
* `roles.role_code`
* `application_types.type_code`
* `applications.application_number`
* `payments.payment_reference`

### CHECK

Used to enforce basic business rules.

Examples include:

* Payment amounts cannot be negative.
* Application fees cannot be negative.
* Approval decisions must use approved values.
* Required text fields cannot contain only whitespace.

---

# 9. Historical Data Strategy

The current application status is stored in `applications.current_status` for efficient operational access.

Historical status changes are stored separately in `application_status_history`.

This provides both:

1. Fast access to the current application state.
2. Complete historical traceability.

The design avoids losing historical information when the current status changes.
